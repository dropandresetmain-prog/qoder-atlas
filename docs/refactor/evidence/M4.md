## 1. Scope actually taken

Event, Programme, ProgrammeItem, Participation/roles, ResourceAssignment,
Place/external refs/associations, GeographicArea/area versions,

## 2. Additive domain contract extensions

`src/domain/v2/programmes/programme.ts` is frozen per `docs/refactor/CONTRACTS.md`
except for additive extensions (§7: "a lane needing a new field adds an
optional field or a new discriminated variant"). Two additions, both
optional/new, neither repurposes an existing field or enum member:

1. `GeographicAreaSchema` — a new root type (`id`, `revision`, `name`,
   `areaType`). M0 materialized only `GeographicAreaVersionSchema` (the
   editions); `DATA_STRUCTURE_LOGICAL_SCHEMA.md` §5 names `geographic_areas`
   as the root those editions belong to, so this fills a genuine omission
   rather than inventing new semantics.
2. `ProgrammeItemSchema.scheduleAuthority` (`'INTERNAL' | 'EXTERNAL'`,
   optional) and `.externalSourceRef` (optional string) — carries M4 brief §F
   ("observed external schedule and internally controlled schedule have
   distinct admission semantics"). Optional so any pre-M4 construction of a
   `ProgrammeItem` literal stays valid; the persistence layer always writes a
   concrete value, defaulting to `INTERNAL`.

Neither change is imported by production composition (still M0's isolation
rule); `test/northstar-v2-contracts.test.ts` does not construct
`ProgrammeItem`/`GeographicArea*` values, so nothing existing could regress.

## 6. Event / Programme / ProgrammeItem ownership

Event is context only — no schedule, no revision-bearing children. Programme
is the single mutable schedule aggregate: ProgrammeItem and Participation are
*children* of the Programme aggregate (registered in `domain_subjects` with
`aggregate_id = programmeId`, no `aggregate_heads` row of their own — the
exact `journey_items`-under-`journeys` shape M2 established). Consequence:
`updateProgrammeItemSchedule`, `setProgrammeItemLifecycleStatus`,
`addParticipation`, `updateParticipation` all advance **the Programme's**
revision, never a second per-item counter. This is the literal mechanism
behind "a programme move must become one canonical state change" — one
`updateProgrammeItemSchedule` call is one `advanceHead` call on one root,
however many rows it touches underneath.

ProgrammeItem cancellation/reinstatement (M4 brief §E) is one typed
transition table (`programmeCommands.ts` `PROGRAMME_ITEM_TRANSITIONS`) where,
unlike Trip/Journey/Event/Programme, `CANCELLED` is **not** terminal:
`CANCELLED -> DRAFT` and `CANCELLED -> SCHEDULED` are both legal, explicit,
separately-submitted commands — reinstatement is never automatic. Landing on
`SCHEDULED` still requires a live window (`programme_items_scheduled_requires_window`
CHECK), so a reinstated item without one must go through `updateProgrammeItemSchedule`
first, landing on `DRAFT`.

## 7. Participation semantics

`participations` has no Journey/Trip column at all — only `programme_item_id`
and `traveller_id`, unique together. A local, non-travelling participant is
representable with zero Journey rows (proven in
`postgres-integration/m4Programmes.pgtest.ts`, "a local participant needs no
Trip/Journey at all"). Multiple Travellers may each hold one Participation on
one ProgrammeItem; one Traveller may hold multiple roles on one Participation
via `participation_roles` (unique `(participation_id, role)`). Acceptance and
attendance are independent, separately-settable dimensions (Closure §4.4).

Where a Journey *does* choose to reflect a Participation — M2's
`engagement_item_details.participation_id` — 0061 makes that a real FK and
0062 adds the cross-table consistency backstop (M4 brief §D): the linked
Participation's `traveller_id` must equal the Journey's `traveller_id`
reached via `journey_items.journey_id`. This is enforced as a deferred
constraint trigger in an M4-owned migration rather than a change to M2's
`travelCommands.ts`, because M2 command/repository files are not this lane's
to edit; the existing `databaseConflict()` mapper in both `travelCommands.ts`
and `programmeCommands.ts` already turns the resulting Postgres exception into
a typed `VALIDATION_FAILED` conflict with no application-layer change needed.

## 8. Internal vs external schedule authority (M4 brief §F)

`programme_items.schedule_authority` (`INTERNAL` default / `EXTERNAL`) gates
`updateProgrammeItemSchedule`: an `EXTERNAL`-authority item refuses the
command outright with a typed `AUTHORITY_DENIED` conflict —
`recordExternalScheduleObservation` is the only accepted path, and it is a
pure, immutable capture into `programme_item_external_observations` that
**never** writes to `programme_items` (verified directly: the window column
stays `NULL` after an observation is recorded against a windowless item).
`conflictsWithCurrent` is computed once at acceptance time by comparing the
observation to the item's *current* stored fields — evidence that the
observation disagreed, not a live assessment (M6 owns assessments).
`setProgrammeItemScheduleAuthority` is the separate, explicit command that
changes who controls a given item's schedule; it is never inferred from an
observation.

## 9. Geography model

Place (operational point, `places`), GeographicArea (versioned spatial root,
`geographic_areas`/`area_versions`) and Jurisdiction (legal regime,
`jurisdictions`/`jurisdiction_areas`) are three structurally distinct tables
with no shared identity and no column that conflates them — a Place has no
geometry column, a Jurisdiction has no polygon or lat/lng column, an Area has
no city-name or airport-code column (`m4Geography.pgtest.ts`, "Place /
GeographicArea / Jurisdiction are structurally distinct").

Geometry is real PostGIS: `area_versions.geometry geography(MultiPolygon,4326)
NOT NULL` with an `ST_IsValid` CHECK (a self-intersecting bowtie polygon is
rejected at COMMIT) and a GiST index; `places.location geography(Point,4326)`
is a generated column from optional lat/lng, also GiST-indexed. Editions are
append-only (shared `forbid_mutation()` trigger — a direct `UPDATE`/`DELETE`
on `area_versions` is rejected). `area_memberships` and `jurisdiction_areas`
are both dated `[valid_from, valid_until)` associations pointing at a
*specific area edition*, not the area's current-latest state, so historical
membership survives a later superseding edition unchanged.

New port `src/contracts/v2/repository/programmeQueries.ts` (additive file,

| Question | Method | Index |

| Externally-authored items pending reconciliation | `externallyAuthoredItemsForProgramme` | `idx_programme_items_external_authority` |

No blast-radius propagation engine is built (M4 brief: "do not build
blast-radius propagation yet") — these are the named, typed, indexed reverse
lookups M6 queries directly.

## 10A. A real bug found and fixed by this lane's own test suite

Writing `m4Programmes.pgtest.ts` against real PostgreSQL caught a genuine
command-layer defect before any external review: `updateProgrammeItemSchedule`,
`setProgrammeItemLifecycleStatus`, `setProgrammeItemScheduleAuthority`,
`addParticipation`, `updateParticipation` and `createResourceAssignment`
resolved the owning Programme (needed to build `expectedAggregateRevisions`)
by calling a `PgProgrammeRepository` method *before* `uow.execute` was ever
called — but every repository method requires the ambient transaction client
`uow.execute` installs via `AsyncLocalStorage`, so the call threw
`currentTransactionClient() called outside an active UnitOfWork.execute
transaction` on every invocation. This produced 16 failing tests on the first
real run.

Fixed by requiring the caller to name `programmeId` explicitly — the same
pattern M2's `updateJourneyItem` already uses (`journeyId` supplied by the
caller, never discovered via a pre-transaction lookup) — with an explicit
ownership-mismatch check once the item/participation is loaded inside the
transaction (typed `VALIDATION_FAILED` on a wrong pairing, never a silent
trust of the caller). `createResourceAssignment` instead moved its owner-ref
resolution *inside* the transaction, since no revision is gated on it and
there was no reason to resolve it early.

Also found and fixed while stabilizing the new tests: a `constructor(private
readonly db: Queryable)` parameter-property in `pgProgrammeReadQueries.ts`
(Node's `--experimental-strip-types` mode used by `node --test` rejects
TypeScript parameter properties); several workspace-mismatch bugs in the test
files themselves (a test would call `fixture()` — which commits one
workspace — and then call `beginSeed()` again, minting a *second*, unrelated
workspace, then mix ids from both); and a raw-SQL parameter-reuse bug in two
`m4Geography.pgtest.ts` negative tests (`$2` was reused for both a `uuid`
column and a `text` column in one `INSERT`, which PostgreSQL rejects outright
as "inconsistent types deduced for parameter $2" — an explicit `::text` cast
on the second occurrence does *not* fix this, since Postgres unifies a
parameter's type across every occurrence in one statement; the fix is a
distinct placeholder for the second occurrence, not a cast).
