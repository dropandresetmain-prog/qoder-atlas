### Confirmed architectural finding — same-Programme bilateral swap

A genuine two-sided programme-item swap (both `CHANGE_PROGRAMME_ITEM_TIME`
effects on programme items belonging to the SAME Programme aggregate) cannot
complete both sides as real ActionIntents through the accepted M7
(`src/resolution/planning/compiler.ts`) -> M8
(`src/persistence/postgres/execution/internalProgrammeExecutor.ts`)
internal-execution pipeline:

- `compiler.ts`'s `CHANGE_PROGRAMME_ITEM_TIME` case always compiles
  `expectedRevisions: []` (unlike its own `CHANGE_SUPPORT_ASSIGNMENT` case,
  which does store a real expected revision) — the frozen v2 `ScenarioEffect`
  shape (`scenarioChange.ts`) never carries a Programme revision either.
- `internalProgrammeExecutor.ts`'s `loadStoredProgrammeSchedule` therefore
  always falls back to a hardcoded `expectedProgrammeRevision: 1`.
- Side A's real execution correctly advances the Programme aggregate (e.g.
  1 -> 2). Side B is then correctly refused `STALE_BASE` by the execution
  gate (the shared strategy's base manifest read that aggregate). A real
  IN-1 re-plan (fresh capture, strategy v2, same effect-scoped logical
  operation key) correctly clears `STALE_BASE` and re-authorizes — but side
  B's execution still fails the real M4 CAS (`STALE_AGGREGATE_REVISION`),
  because the hardcoded `1` fallback is now genuinely stale, and nothing in
  the compiled intent or the executor can express the real current revision.

Fixing this needs one of: a frozen v2 contract change, a `compileActionPlan`
signature change (it does not receive the base world today), or relaxing the
M8 execution gate's currentness semantics — all M7/M8 contract changes, out
of scope for M9 integration work. Not routed around (e.g. by calling
`updateProgrammeItemSchedule` directly outside the ActionIntent/execution
layer for the second side, which is exactly the "move Sarah only" shortcut
C4 already rejected).
