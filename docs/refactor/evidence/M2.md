## 2. The first real non-WORKSPACE typed-subject pattern (C1 amendment b)

M1 installed the constraint trigger in `0003_identity_registry.sql` with one
hard-coded `WORKSPACE` branch and told later lanes to `CREATE OR REPLACE` the
whole function. Four parallel lanes doing that would each delete the others'
branches at integration. M2 replaces the *mechanism*, not the rule:

- `0010` owns `subject_subtype_checkers (kind PK → subject_kinds, checker_function
  text CHECK ~ '^[a-z_][a-z0-9_]*$', installed_by)` and rewrites
  `enforce_domain_subject_subtype()` as a dispatcher that does
  `EXECUTE format('SELECT %I($1,$2,$3,$4)', v_checker)`.
- M1's WORKSPACE predicate moved **verbatim** into
  `enforce_subject_subtype_workspace()` and is registered with
  `installed_by = 'M1'`. No accepted-C1 semantics changed.
- Fail-closed is preserved: an unregistered kind raises
  `domain_subjects subtype violation: kind % has no installed typed-table
  enforcement`, and a registry row naming a missing function raises
  `... checker % registered for kind % is not installed`. `0010` adds no
  default-allow branch, so M3/M4/M5 kinds stay rejected until their owner
  installs a checker. The M1 case in
  `postgres-integration/tenantIntegrity.pgtest.ts` ("a pre-registered kind
  without an installed typed-table branch is rejected") still passes under M2,
  and `m2SubtypeIntegrity.pgtest.ts` re-proves it for
  `RESERVATION`/`PLACE`/`ASSESSMENT` — kinds M2 does not own.
- The `%I` interpolation is why `checker_function` is a bare identifier under a
  CHECK rather than a `regproc`: the dispatcher can never receive a qualified or
  expression-valued name.

A checker proves two things: the typed row exists for `(workspace_id, id)`, and
the subject's `aggregate_id` matches the Schema §1 ownership rule for that kind
(self for roots, the parent for children). Where a relationship cannot be
expressed by an ordinary FK, the checker closes it too — e.g.
`enforce_subject_subtype_traveller` additionally rejects a
`travellers.display_name_ref` that selects another traveller's
`traveller_names` row, which no single-column FK can prevent.

`JOURNEY_ITEM` is the deliberate child case: it is a registered non-WORKSPACE
subject with **no `aggregate_heads` row of its own**, so its version advances
with the Journey. `m2SubtypeIntegrity.pgtest.ts` asserts both halves
(`count(*) FROM aggregate_heads` = 0 for the item, `domain_subjects.aggregate_id`
= the Journey's id).

### Extension contract for M3/M4/M5 (also in `0010`'s header comment)

1. `CREATE FUNCTION enforce_subject_subtype_<kind>(p_workspace_id uuid, p_id
   uuid, p_kind text, p_aggregate_id uuid) RETURNS void LANGUAGE plpgsql`,
   raising messages that start `domain_subjects subtype violation:`.
2. `INSERT INTO subject_subtype_checkers (kind, checker_function, installed_by)`
   with `installed_by` set to the milestone.
3. Never edit `0010`, the dispatcher, or another lane's checker.

Because the trigger fires as `DEFERRABLE INITIALLY DEFERRED`, a lane's typed row
may be written before or after its `domain_subjects` row inside the same
transaction — the contract does not force a registration order on future lanes.

## 3. Frozen identity semantics made structural

| Decision | Where it stops being a convention |
|---|---|
| Traveller is a stable person; names/contacts are dated children | `0012`: no name or contact column on `travellers`; `display_name_ref` is a deferred FK to `traveller_names`, cross-checked by the `TRAVELLER` checker. `name_kind IN ('LEGAL','DISPLAY','PREFERRED','OTHER')` with `valid_from`/`valid_until`/`evidence_id`. |
| Identity is not derived from events, bookings, suppliers or fixtures | `0012` has no event/booking/supplier-locator/fixture-derived column at all, so a provider record cannot silently define a person. Merge requires the explicit `MERGED` transition + `merged_into_traveller_id` (`travellers_merge_shape`, `travellers_not_self_merge`); an inferred merge is not expressible. |
| Trip is a shared undertaking; Journey is one traveller's participation | `0020`/`0021`: a Trip commits no meaning without journeys, and `journeys` carries a unique index on `(workspace_id, trip_id, traveller_id)` — exactly one Journey per Traveller per Trip, no "main"/"sub" traveller column. |
| Relationship ≠ responsibility ≠ authority | Three separate root subjects and tables (`0017`, `0018`, `0019`) with three checkers. `responsibility_role_subject_kinds` and `authority_action_kinds` are FK'd vocabularies, not strings that grant powers. |
| Accompaniment requirement ≠ who actually supports | `0027` is the governing, append-only requirement keyed `(workspace_id, id, version)`; `0028` records the selected fulfilment. `support_assignments_requirement_fk` is a composite FK to the **exact requirement version**, so an assignment cannot silently track a later requirement edit, and no `accompaniment_requirements` row can be mutated in place. There is no `is_supported` / `has_support` / supported-flag column anywhere — asserted by `m2SubtypeIntegrity.pgtest.ts`. |
| Credentials are Traveller-owned; the Journey only *selects* | `0014`/`0015`/`0025`: `travel_credentials`/`credential_versions` are owned by a Traveller; `credential_selections` is the Journey-side choice with one selection per Journey and per-selection visit links. Protected values stay as the `ProtectedDataRef` triple (`value_content_hash`, `value_storage_ref`, `value_access_policy_id`) — `0012` contacts and `0015` document numbers have no plaintext fallback column. Missing credentials remain an explicit absence, never a guessed `PASS`; entry feasibility is M6's decision. |
| Journey intent ≠ supplier truth | M2 has no booking reference, reservation, allocation, supplier locator or offer column anywhere in `0010`–`0029`. `journey_items` + `0023` detail tables record *intent*; M3 owns the arrangement side. This is the reason one real booking cannot be duplicated across every Journey: there is nowhere in M2 to put it. |

## 4. C1 amendment confirmations

- **(a) `TypedRef` is `(kind, id)` and a wrong kind must fail even when the UUID
  exists.** `domain_subjects (workspace_id, id, kind)` is a real discriminating
  FK target (unique index `domain_subjects_workspace_id_id_kind_uidx`, `0019`),
  used by `authority_grants_represented_party_fk` and `grant_scopes_subject_fk`.
  `m2SubtypeIntegrity.pgtest.ts` proves both relabelling directions with a probe
  table that carries a *surrogate* PK, so the rejection demonstrably comes from
  the FK and not from a duplicate key, and `PgSubjectRegistryReadQueries.resolve`
  /`resolveAll` return `undefined`/omit a ref whose kind does not match, while
  `('TRIP', <a Journey uuid>)` resolves to nothing.
- **(b) Fail-closed subtype registration.** §2 above: valid row + subject + head
  commit atomically; a subject cannot commit without its typed row; wrong kind
  fails; unregistered future kinds stay rejected; probes leave **zero residue**
  (post-rollback counts of checkers / functions / probe tables / subjects are all
  `0`).
- **(c) Retry-safe `execute()`.** Every M2 command handler generates all
  identifiers it will report *before* the retryable callback and performs no
  provider, network or irreversible work inside it. `PgUnitOfWork.execute` retries
  on SQLSTATE `40001`/`40P01` (3 attempts), so a partially-generated id would be a
  correctness bug, not a style one. The mechanism is proven by
  `postgres-integration/serializableRetry.pgtest.ts`: two genuinely concurrent
  scope-generation advances both completing with no lost update, and a forced
  `40001` exhausting to a typed conflict after rollback. The M2-level property is
  now proven too. `m2People.pgtest.ts` "a handler replayed after a forced 40001
  leaves the same rows as one that never failed" wraps a real `UnitOfWork` so the
  *first* attempt of `APPEND_CREDENTIAL_VERSION` performs the handler's own writes
  and is then aborted by a server-raised `40001`; it asserts the callback ran
  exactly twice, the command still committed, and the full typed row set
  (`travel_credentials`, `credential_versions`, `passport_details`) is identical,
  after normalising only the caller-pinned ids and the `*_at` stamps, to a control
  run of the same command that never conflicted — with exactly one version row and
  one detail row, so the aborted attempt left nothing behind. Residual, recorded
  as G7: one handler per aggregate family is instrumented, not all 34.
- **(d) Command-result replay via `CommandReceipt.resultRef`.** The receipt's
  `resultRef` is the JSON serialization of the committed result — not an opaque
  pointer. `buildReceipt` (`src/persistence/postgres/commandSupport.ts`) encodes
  it; `PgUnitOfWork.execute` decodes it on the `REPLAY` branch of
  `IdempotencyLedger.claim` and returns without invoking the handler. This
  post-C0 clarification is recorded as §8 of `docs/refactor/CONTRACTS.md` — the
  only change made to that file, and it adds/removes/repurposes no field, enum
  member or discriminated-variant.

## 6. Revision and scope behaviour

M2 introduces no new concurrency mechanism; it is the first lane to exercise
M1's at scale. A root command: `lockHeads` on every aggregate it will touch →
reject when the caller's `expectedRevision` is not the locked revision
(`staleRevisionConflict`) → check the declared scope generations are still
current → write typed rows + `domain_subjects` + `aggregate_heads` +
`change_records` → `CommandReceiptSchema.safeParse` the result → insert the
receipt → COMMIT. The `aggregate_heads` row is written before the
`domain_subjects` row where a circular deferred FK requires it, and the inverse
ordering is left to the deferred constraint trigger where the typed row must
exist first; both orders are exercised by `m2Seed.ts` and the command handlers.
Child subjects never get a head row (§2). No external call happens inside any
transaction.

## 7. Reverse-lookup decisions (`0029`)

`0029` exists because the read operations that decide these access paths belong
to M6 (applicability / reassessment) and M9 (authority / execution), while the
tables belong to M2 — and both are required to answer reverse questions in SQL
rather than by parsing JSON. Each of the 11 indexes names the lookup it exists
for. The consequential ones:

- Journeys by `(traveller_id, window)` and `(trip_id, window)`, partial on
  `intended_window_start IS NOT NULL` — the bounded candidate set every
  entry/advisory evaluation starts from.
- `group_memberships (group, window)` and `coordination_groups (window)` — a
  group's roster at a moment in time.
- `travel_credentials (current_version_id)` and
  `credential_versions (expiry_date)` — an issuer status change or new accepted
  edition finds the credentials and journeys that depend on it.
- `grant_actions (action_kind, grant_id)` and
  `authority_grants (principal_id, issued_at DESC)` — "may this principal do
  exactly this action over exactly this subject at this instant" without scanning
  grants; an unregistered action never reaches the lookup because `grant_actions`
  is FK'd to the closed 12-entry M2 vocabulary.
- `profile_assertions (workspace_id, assertion_type, traveller_id)` — "which
  travellers currently assert X". Deliberately **not** partial on
  `supersedes_assertion_id IS NULL`: `0013` is append-only, so an edition becomes
  history only when a later row points at it through `supersedes_assertion_id`,
  and that predicate would pin each chain's *first* edition and report superseded
  facts as current. Currentness is an anti-join served by
  `idx_profile_assertions_supersedes`; `idx_profile_assertions_by_type` covers
  the type-driven scan itself.
- `traveller_contacts (value_content_hash)` — duplicate detection compares hashes
  because the plaintext never lands in this database.
- `accompaniment_eligible_supporters (requirement_id, requirement_version)` —
  "what covers this traveller's requirement right now" and the reverse question
  used by the shared-disruption case.

M2 deliberately builds none of the M6 dependency engine or Resolution Graph. It
ships the columns and access paths so M6/M9 never have to parse JSON: `0023` uses
`jsonb` only for bounded opaque detail under `jsonb_typeof(...) = 'object'`
CHECKs, and any field a reader would filter on was made a column instead.

## 8. Legacy mapping and ambiguities

Recorded in `docs/refactor/MIGRATION_MAPPING.md` §7 (rules the schema now
enforces), §7.1 (staging) and §7.2 (deferral ledger). The three that were
genuinely ambiguous and are now decided rather than guessed:

1. `entities.TRAVELLER` and `booking_dossiers` are **merged** into
   `travellers` + `traveller_names` + `traveller_contacts` + `profile_assertions`.
   Conflicting names become two dated rows plus the `display_name_ref` pointer —
   never a silent overwrite, and the checker makes a cross-person display
   inexpressible. Duplicate people become `lifecycle_status = 'MERGED'` with
   `merged_into_traveller_id`.
2. `passports[]` / `nationalityCodes[]` split: a *document* is a
   `travel_credentials`/`credential_versions` row with a `0015` typed detail
   table; a *personal fact* (DOB, gender, nationality asserted about the person)
   is a `profile_assertions` edition. Sensitive values import only as the
   `ProtectedDataRef` triple.
3. `Trip.travellerIds[]` → one Journey per entry, with the unique index making
   "exactly one" enforced and `elements[]` owner ambiguity flagged for
   reconciliation instead of guessed. `BookingRef` and `Stay.guests` occupancy are
   explicitly **not M2** — M3 owns reservations and allocations.

Ambiguous identity never lands on a typed table: `legacy_id_map` is append-only
(`legacy_id_map_immutable` rejects UPDATE and DELETE via `forbid_mutation()`), its
natural key is `UNIQUE (workspace_id, source_dataset, source_type, source_id)`,
its `target_kind` is FK'd to the closed `subject_kinds` registry, and
`mapping_evidence` is NOT NULL. `migration_runs.reconciliation_exceptions` (a
`jsonb NOT NULL DEFAULT '[]'` array) is the only landing zone for unresolved
identity, and no legacy-source column exists on any M2 typed table. That shape is
what makes the mapping auditable rather than implied.

### 13.2 Process findings worth carrying forward

* **`node --test` strips types; it does not compile them.** A TypeScript parameter
  property in a test-visible class fails the *canonical* gate with
  `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` while passing under `tsx`. The same parser
  rejected an `await` inside a non-`async` arrow while `tsc` also caught it. Fix in
  source, never by switching the gate to `tsx`: a `tsx`-green suite is not evidence.
* **A command that mints its own ids is not replayable.** Retrying a transaction
  whose callback calls `randomUUID()` writes different rows than its receipt
  describes, so ids must be pinned before `execute()`. This is now a named test
  rather than a comment.
* **EXPLAIN-based assertions need the incidental access paths removed, including
  the scanned table's own primary key.** `(workspace_id, id)` leads with the
  partition column, so it is a legitimate alternative plan — and the planner only
  reaches for it once autovacuum has statistics. On a cold database
  `idx_journeys_traveller` won the cost tie; on the warm one the same statement
  planned as a primary-key lookup that *filters* `traveller_id`, and the assertion
  failed for a reason unrelated to the schema. `m2Travel.pgtest.ts` now drops the
  PK constraints (`CASCADE`, inside the rolled-back measurement transaction) for the
  tables carrying each statement's own predicate, while keeping join-side keys in
  place, because those are the path a correct plan is meant to use. The test
  measures *usability*, not a tie-break, so it holds either way.
* **The PostgreSQL test database is shared and tmpfs-backed.** All four M2 suites
  plus M1 run against one container owned by compose project `qoder-atlas`, so
  `db:postgres:down` cannot name the container, and editing any already-applied
  migration invalidates every lane's checksum ledger at once. In-place reset is
  `DROP SCHEMA public CASCADE; CREATE SCHEMA public; GRANT …`, and lanes must finish
  before a migration is touched — which is exactly why G3 was sequenced last.
* **No implementation barrel.** M2 exports through the frozen
  `src/contracts/v2/repository/index.ts` and left `src/contracts/v2/index.ts`
  untouched, so nothing can reach an M2 repository without naming it.
* **`credential_links` is write-only in M2.** Nothing reads it yet; the reverse
  lookup it serves belongs to M5/M6. **Park for Later** — a read path should arrive
  with the consumer that needs it, not before.
