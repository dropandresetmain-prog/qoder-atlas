### Notable schema design decisions

- **Circular deferred FK for atomic registration** (0003): `domain_subjects.aggregate_id
  REFERENCES aggregate_heads` and `aggregate_heads.aggregate_id REFERENCES
  domain_subjects`, both `DEFERRABLE INITIALLY DEFERRED`, so a command can
  insert the typed row, the head, and the subject in one transaction in any
  order — checked only at `COMMIT`, matching the logical schema's "deferred
  constraints for the circular identity relationship."
- **Subtype enforcement** via `enforce_domain_subject_subtype()`, a deferred
  constraint trigger. M1 owns only the `WORKSPACE` branch; every other
  pre-registered kind fails closed until its owning M2-M5 migration replaces
  the function with an explicit typed-table branch. This prevents an untyped
  registry/head pair from becoming authoritative before the typed table exists.
- **Append-only enforcement** via a generic `forbid_mutation()` trigger
  function, attached to `command_receipts`, `change_records`,
  `inbox_deliveries`, and `legacy_id_map` — immutability is a database
  boundary, not only an application convention.

### Why the integration suite lives in `postgres-integration/`, not `test/`

`node --test` (the repository's default `npm test`) discovers **every** file
under any directory literally named `test`/`tests`, regardless of filename —
not just files matching a `*.test.*` pattern. Naming these files
`*.pgtest.ts` inside `test/persistence/postgres/` was tried first and did
**not** exclude them: `npm test` still swept them in and failed with
`ECONNREFUSED` once the Postgres container was torn down, which would have
broken the credential-free default suite for every future contributor who
doesn't happen to have `db:postgres:up` running. The suite was moved to a
repository-root `postgres-integration/` directory (verified empirically:
after the move, `npm test` no longer references any `postgres-integration`
path and does not fail without Postgres running — see the full-baseline
result below). `tsconfig.json`'s `include` and `eslint.config.js`'s
`test/**/*.ts` overrides were both extended to also cover
`postgres-integration/**/*.ts` so it stays typechecked/linted.

## Repository / UnitOfWork / durable-work behaviour implemented

All in `src/persistence/postgres/`:

- `pgUnitOfWork.ts` — `PgUnitOfWork implements UnitOfWork`. Every `execute()`
  call runs the entire command body at **SERIALIZABLE** isolation with
  bounded whole-transaction retry (3 attempts, `40001`
  serialization_failure / `40P01` deadlock_detected only) — chosen uniformly
  rather than per-command READ COMMITTED-vs-SERIALIZABLE branching, at some
  conservative throughput cost flagged below as a later tuning candidate, not
  a correctness gap. Retry exhaustion returns the explicit typed
  `SERIALIZATION_RETRY_EXHAUSTED` conflict after rollback, never a raw partial
  success. Order of operations matches
  `DATA_STRUCTURE_LOGICAL_SCHEMA.md` §11.1 exactly: advisory-lock claim →
  idempotency lookup (REPLAY/HASH_MISMATCH short-circuit before `fn` runs) →
  lock affected heads in ascending-id order → validate expected
  revisions/scope generations → call `fn` → insert the immutable receipt →
  commit.
- `pgAggregateHeadReader.ts` / `pgIdempotencyLedger.ts` /
  `pgScopeGenerationLedger.ts` — the three `UnitOfWork` sub-interfaces.
  Design note recorded because it is a real (non-semantics-changing)
  interpretation of an underspecified corner of the frozen contract: neither
  `TypedRef` nor `AggregateHeadReader`/`ScopeGenerationLedger`'s methods carry
  a `workspaceId` parameter, so those two readers are workspace-bound at
  construction (one `PgUnitOfWork` instance per workspace via
  `unitOfWorkFor(workspaceId)`); `IdempotencyLedger.claim` **does** take
  `workspaceId` explicitly per the frozen signature and is implemented
  accordingly, not construction-bound.
- `transactionContext.ts` — an `AsyncLocalStorage<PoolClient>` exposing the
  active transaction's client to domain-handler code (`currentTransactionClient()`)
  without widening `UnitOfWork.execute`'s frozen `fn` callback signature.
- `advisoryLock.ts` — deterministic FNV-1a64 → signed-bigint key for
  `pg_advisory_xact_lock`, scoping the idempotency claim to exactly one
  (workspace, commandType, idempotencyKey) tuple per transaction.
- `workspaceCommands.ts` — reference domain handlers
  (`registerWorkspace`/`renameWorkspace`) proving a handler can persist typed
  rows, advance a head, append a change record + outbox row, and receive a
  committed receipt, entirely through the `UnitOfWork` boundary — **no SQL
  outside `src/persistence/postgres/**`**. This is the concrete demonstration
  behind the acceptance line "domain handlers can operate through the target
  UoW/repository contracts without direct SQL in the engine": nothing under
  `src/engine/**` issues SQL, and nothing in this package added such a
  dependency.
- `claimQueue.ts` — `FOR UPDATE SKIP LOCKED` claim + fencing-token primitives
  shared by `inbox_work` and `outbox`. Reclaiming an expired lease is folded
  into the same claim query (bumps `fencing_token`), so a stale worker's
  later `complete*`/`fail*` call — which must present the fencing token it
  was originally handed — matches zero rows and is refused.
- `inbox.ts` — `deliverInboxMessage`: capture + resumable per-target work
  creation in one transaction; same-key/same-hash is an idempotent no-op,
  same-key/different-hash is quarantined into `inbox_delivery_conflicts`
  (never overwrites the original capture).
- `migrate.ts` — the ordered/checksummed runner described above;
  `MigrationChecksumDriftError` / `MigrationApplyError` are distinct typed
  failures.
- `composeTargetRuntime.ts` — the construction seam: builds a `Pool`, runs
  migrations, returns `unitOfWorkFor(workspaceId)`. **Not imported by
  `src/main.ts` or `src/app/compose.ts`.**
- `config.ts` — `PG_TARGET_*`/`PGTEST_*` env vars, entirely separate from
  `src/config/config.ts#loadConfig()`.

### Cold-start connection note (diagnosed and fixed in the test harness)

The first `test:postgres` run immediately after a fresh `db:postgres:up`
reliably hit `Error: Connection terminated unexpectedly` on the first real
connection, across several independent reproductions. Root cause: the
official `postgres`/`postgis` Docker image starts a **temporary** server to
run init scripts (creating the `template_postgis` database and loading
extensions into it and into `northstar_test`), stops it, then `exec`s the
real long-running server. `pg_isready` — and therefore `docker compose up
--wait`'s healthcheck — can report the *temporary* server as ready; a client
connecting in the gap between temp-server-stop and real-server-start gets
`Connection terminated unexpectedly`. Confirmed via `docker logs
northstar-postgres-test`, which shows a full CREATE DATABASE/CREATE
EXTENSION sequence for `template_postgis` and `northstar_test` after the
first "database system is ready to accept connections" log line.

Fixed in `postgres-integration/harness.ts`'s `waitUntilReady`: each attempt
opens a throwaway `pg.Client` (never a possibly-now-dead pooled connection)
and requires **two consecutive successes one second apart** before declaring
the server stable, up to 40 attempts (~30s ceiling) — a single lucky ping
during the temporary server's last moment can't pass this. After the fix, a
cold `db:postgres:down && db:postgres:up && test:postgres` cycle took ~16s
to stabilize on its first query and then ran cleanly; the C1 follow-up suite
now covers 28 tests, reproduced after a disposable-volume reset.
twice. This is a test-harness concern only — `PgUnitOfWork`/the migration
runner themselves make no assumption about container startup timing, and
production PostgreSQL instances (not disposable per-test-run containers)
don't cycle through a temporary server on every connection attempt.
Classified **Ignore / Accept Risk** for production relevance, but the fix is
real (not merely documented around) so `npm run test:postgres` is reliably
runnable standalone by a future engineer without tribal knowledge of this
quirk.

## Concurrency / transaction evidence

All concurrency tests use **`Promise.all` over two separate `PgUnitOfWork`
instances (or two direct `pool.query`/claim calls) against the same `pg.Pool`**
— each `execute()`/claim call checks out its own `PoolClient`, so this is two
genuinely independent PostgreSQL connections/backends, not simulated
interleaving on one connection. Postgres server: 16.4. PostGIS: 3.4.3.

- **Stale expected revision fails, state unchanged** —
  `revisionConflicts.pgtest.ts` "a stale expected revision fails...".
- **Equal-revision reuse after a commit is impossible** — same file,
  sequential same-`expectedRevision` attempts: the second is rejected
  `STALE_AGGREGATE_REVISION` after the first commits.
- **Concurrent writers, no lost update** — same file, "concurrent writers
  racing on the same expected revision": two independent connections race
  `renameWorkspace` with the same `expectedRevision`; exactly one succeeds,
  the other gets a typed conflict (either directly from the CAS check, or —
  when the second connection's `SELECT ... FOR UPDATE` blocks behind the
  first's row lock and then wakes to find the row changed — via an internal
  `40001` that `PgUnitOfWork.execute`'s bounded retry transparently absorbs
  before returning the clean typed conflict); final `aggregate_heads.revision
  = 2` (not 3, not stuck at 1), and the persisted name matches the winner.
- **SERIALIZABLE predicate conflict + bounded retry, explicitly proven** —
  `serializableRetry.pgtest.ts`: two independent connections both call
  `scopes.advance()` on the *same* scope concurrently; both resolve `ok:
  true` (if the automatic retry did not work, one would reject with an
  unhandled `40001` instead), final `generation = 2` — both increments
  applied, none lost.
- **Retry exhaustion is typed and rolled back** — same file forces a real
  PostgreSQL `40001` with a one-attempt UoW and receives
  `SERIALIZATION_RETRY_EXHAUSTED` rather than a raw driver error.
- **Idempotency replay returns the original receipt** —
  `idempotency.pgtest.ts`: replaying `registerWorkspace` with the same key
  and payload returns the *same* `committedAt`/value and does **not**
  attempt a second `INSERT` (a real duplicate-key error would surface
  immediately if the replay short-circuit were broken).
- **Idempotency key reuse with a different payload fails closed** — same
  file: `IDEMPOTENCY_KEY_PAYLOAD_MISMATCH`, no domain-state change.
- **Replay payload and envelope binding are validated** — same file rejects an
  opaque `resultRef` before commit and rejects a receipt whose idempotency key
  differs from the envelope, so a receipt cannot poison or diverge from its
  command's idempotency identity.
- **Atomic multi-table commit** — `atomicCommit.pgtest.ts`: one
  `registerWorkspace` call produces exactly one row each in `workspaces`,
  `aggregate_heads`, `domain_subjects`, `change_records`, `outbox`, and
  `command_receipts`.
- **Transaction rollback on failure** — same file: a handler that performs
  two successful writes and then throws leaves **zero** rows in either
  table; a handler that returns a typed conflict after a write also leaves
  zero rows.
- **Competing workers cannot both own the same claim** —
  `inboxOutbox.pgtest.ts`: two concurrent `claimNextInboxWork` calls against
  one pending row — exactly one wins (`FOR UPDATE SKIP LOCKED`).
- **Durable work survives a simulated crash; expired claims recover; stale
  worker fenced out** — same file, one flow: claim → (simulated crash,
  no completion) → row still durably `CLAIMED` → lease manually expired →
  second independent claim succeeds with a bumped `fencing_token` → the
  *original* claimant's `completeInboxWork` now returns `false` (fenced) →
  the *current* claimant completes successfully.
- **Workspace/tenant FK integrity** — `tenantIntegrity.pgtest.ts`: a
  `domain_subjects` row cannot reference another workspace's
  `aggregate_heads` row; `aggregate_heads` rejects an unknown
  `workspace_id`; the subtype trigger rejects a self-inconsistent
  `WORKSPACE` subject; `aggregate_heads` carries exactly one revision row
  across the full command lifecycle.
- **Typed head identity and uninstalled subtypes fail closed** — same file
  proves a `TRIP` reference cannot load or lock a `WORKSPACE` head with the
  same UUID, and a pre-registered `TRIP` cannot commit without an installed
  typed-table enforcement branch.
- **Migration integrity** — `migrate.pgtest.ts`, against fresh throwaway
  databases created per test (`CREATE DATABASE`/`DROP DATABASE ... WITH
  (FORCE)`): empty-database bootstrap creates every expected table plus a
  working PostGIS install; a failing migration rolls back completely and is
  never recorded in `schema_migrations`; re-running on an
  already-fully-migrated database is a clean no-op; corrupting a recorded
  checksum makes the runner refuse to proceed (`MigrationChecksumDriftError`)
  without applying anything further.

## Failure / rollback behaviour demonstrated

- Migration failure: DDL inside the failing migration's own transaction
  rolls back completely (Postgres DDL is transactional); the ledger records
  nothing for that version; migrations strictly before it remain applied.
- Command failure (thrown exception or returned typed conflict): the whole
  transaction rolls back — proven for both cases in `atomicCommit.pgtest.ts`.
- Idempotency hash mismatch: rejected before any domain write is attempted.
- Expected-revision/scope-generation mismatch: rejected before `fn` runs at
  all (checked in `runBody` before calling the handler).
- Worker fencing: an expired-then-reclaimed claim cannot be completed by the
  stale claimant; `failInboxWork` also respects fencing.

## Unresolved architecture gaps encountered

None. No accepted C0 contract needed a semantics change. The one genuine

`workspaceId` that must match the bound one).
